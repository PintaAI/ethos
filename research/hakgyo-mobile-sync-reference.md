## What is actually implemented

| Area | Hakgyo behavior | Ethos adaptation value |
| --- | --- | --- |
| Durable outbox | SQLite operations keyed by `(user_id, id)`; payload upsert resets failure counters only when the payload changes. Local write queue serializes changes. | Preserve stable operation identity; add explicit payload/version identity for acknowledgment. |
| Checkpoint scheduling | Checkpoints coalesce by scope and local write version, then execute on one checkpoint promise chain. A write arriving during upload changes the version so a later checkpoint can run. | One orchestrator can combine foreground, reconnect and mutation triggers without dropping the follow-up work. |
| Acknowledgment | Before deleting an acknowledged operation, compare its current JSON payload to the exact sent payload. New edits during the request remain queued. | Particularly valuable for edits to an already pending transaction or account. |
| Batch draining | Client batches 50 operations, reads up to 5,000 per checkpoint, handles partial acknowledgments and unprocessed operations, bounds request count, stops on no progress. Server maximum is separate from client batch size. | Bound request size and drain backlog without requiring another user action; preserve dependency ordering. |
| Failure policy | Transient failure stops later dependent work. Terminal failures count only against unchanged operations; quarantine requires at least five failures and 24 hours. | Use structured error classes, retain recoverable failures, expose actionable blocked operations. Do not adopt deletion/retention limits for financial data. |
| Download freshness | Manifest supplies index token, course revisions, schemas and next-check interval. Index endpoint can return unchanged; bundles use revisions and ETags. | Adopt scoped invalidation or revisions only where Ethos needs it; do not replace a functioning delta protocol with course bundles. |
| Network and timing | Foreground-only automatic checks, reconnect subscription, startup jitter, retry jitter, server-directed polling interval. | Reduce redundant requests and burst load while maintaining prompt explicit writes. |
| Protocol evolution | Requests carry protocol 2; shared minimum protocol and separate bundle/index schemas. Unsupported protocol activates update gate. | Negotiate capabilities/version independently of local DB version and EAS native runtime. |

## Scheduling details

The root navigator maintains scope, `nextAttemptAt`, failure count and running flag. Launches with local data and an empty queue spread checks across 60 seconds; otherwise across five seconds. Explicit actions call checkpoints immediately. Automatic success checks occur no sooner than 15 minutes, honoring a longer server interval. Retry base starts at 30 seconds (`15 seconds * 2^failureCount`), caps failure count at six, and adds up to another base of random jitter. Thus the current code reaches 16–32 minute retry delays, despite the separate one-hour cap expression. Reconnection advances the next attempt to within five seconds. A 30-second timer and app foreground event feed the same guard. These values fit learning-content freshness and should not be copied as financial-data SLAs. [Scheduler](/root/projects/hakgyo-v2/apps/mobile/app/_layout.tsx:69).

`checkForUpdates` uploads pending operations first and will not refresh if any remain. This protects a server refresh from immediately replacing optimistic state, but a persistent bad queue item can delay fresh server reads until it is resolved/quarantined. Ethos should explicitly decide whether reads can proceed while retaining a local pending overlay. [Update sequencing](/root/projects/hakgyo-v2/apps/mobile/src/sync/engine.ts:1106).

Bundle downloads have their own deduplicated jobs, bounded concurrency, user-request priority, exponential retry and ETag handling. This is useful for large attachments/read caches, not a reason to parallelize dependent financial mutations. [Bundle worker](/root/projects/hakgyo-v2/apps/mobile/src/sync/bundle-sync.ts:87).

## Server semantics and conflict limitations

The server processes operations individually. Validation failure belongs to one operation; time-budget exhaustion leaves untouched operations unacknowledged, and transient failure stops the sequence. Assessment retries consult durable domain state and compare stored answers before acknowledging. Vocabulary operations delegate to vocabulary-domain handling, and content completion delegates to a domain mutation. This is domain-specific replay handling, not evidence of a generic receipt ledger for arbitrary mutations. Do not assume the same replay safety applies to Ethos money transfers or amount adjustments without checking its server. [Apply operations](/root/projects/hakgyo-v2/apps/web/src/server/mobile/apply-operations.ts:199), [commit router](/root/projects/hakgyo-v2/apps/web/src/server/api/routers/mobile-sync-v2.ts:130).

Hakgyo applies learner/gamification patches and later refreshes server state; the inspected engine does not establish a general field-level conflict-resolution scheme. A confirmed assessment whose offline answers differ returns a precondition failure rather than silently acknowledging those answers. Ethos needs its own conflict rule for concurrent money edits; operation replay identity, entity revision and UI resolution are distinct concerns. [Patch merging](/root/projects/hakgyo-v2/apps/mobile/src/sync/engine.ts:376), [assessment replay checks](/root/projects/hakgyo-v2/apps/web/src/server/mobile/apply-operations.ts:284).

Freshness uses revision tokens, not a paginated change cursor at the mobile boundary. The server revision query takes the newest transaction ID below the current snapshot horizon; the design documentation describes database-triggered change logging and compaction. Copying that design would require server schema and trigger coverage work, not merely a mobile OTA. [Revision query](/root/projects/hakgyo-v2/apps/web/src/server/mobile/sync-log.ts:25), [design notes](/root/projects/hakgyo-v2/docs/mobile-sync.md:5). A trigger audit/compaction proof was outside this bounded mobile-reference review.

## Protections and gaps that must not be copied blindly

1. **Quarantine truncation is inappropriate for unsynced money changes.** Dead-letter movement is transactional and stores the full operation, but retains only the newest 50 entries. Ethos should retain financial operation payloads until an explicit recovery/discard decision and provide retry/export/diagnostic paths. [Dead-letter transaction](/root/projects/hakgyo-v2/apps/mobile/src/sync/store.ts:1002), [retention constant](/root/projects/hakgyo-v2/apps/mobile/src/sync/store.ts:18).

2. **User-scoped SQLite rows do not by themselves prove account-switch safety.** Rows use user keys, but a confirmed sign-out clears all users' queued operations and caches. Offline/session-check errors avoid this wipe. `dispose()` waits for checkpoint and write tails, yet does not await active refreshes; bundle disposal stops queued jobs but not in-flight fetch/apply. Late refresh/download completion can still reach query-cache publication after teardown, so the reference is not proof against stale account writes. Ethos should use an account generation guard and request cancellation/finally checks around every post-await commit. [Session setup/teardown](/root/projects/hakgyo-v2/apps/mobile/src/providers/MobileSyncProvider.tsx:137), [confirmed sign-out clear](/root/projects/hakgyo-v2/apps/mobile/src/providers/MobileSyncProvider.tsx:64), [all-data wipe](/root/projects/hakgyo-v2/apps/mobile/src/sync/store.ts:793), [engine dispose](/root/projects/hakgyo-v2/apps/mobile/src/sync/engine.ts:1161), [bundle dispose](/root/projects/hakgyo-v2/apps/mobile/src/sync/bundle-sync.ts:394), [query publication](/root/projects/hakgyo-v2/apps/mobile/src/sync/engine.ts:304). The late-completion concern is a source-based risk inference, not a reproduced failure.

3. **Local migrations contain both safe additive work and destructive work.** Schema initialization creates tables idempotently, probes existing outbox columns and adds failure fields. Legacy dead letters migrate transactionally into the new table, then the old table is dropped; the old `mobile_sync_cache` is also dropped. Additive columns are an adaptation candidate. Dropping old tables is not rollback compatible for an earlier OTA expecting them. [Migration](/root/projects/hakgyo-v2/apps/mobile/src/sync/store.ts:284).

4. **Cache reset and sign-out differ.** User-requested cache clearing flushes first and refuses if operations remain. The store cache-only method preserves the queue. Confirmed sign-out takes the destructive all-data path described above. Ethos should separate account privacy, queue retention and cache rebuild policy explicitly. [Resync flow](/root/projects/hakgyo-v2/apps/mobile/src/providers/MobileSyncProvider.tsx:385), [cache-only deletion](/root/projects/hakgyo-v2/apps/mobile/src/sync/store.ts:775).

5. **A forced update gate is not OTA compatibility.** Raising the minimum protocol blocks older clients. For Ethos, preserve the old API while migrating users, negotiate optional capabilities, and only require a new client when an installable compatible update/build exists. Separate data migration rollback tests remain necessary. [Protocol constants](/root/projects/hakgyo-v2/packages/shared/src/mobile-sync/types.ts:15), [gate condition](/root/projects/hakgyo-v2/apps/mobile/app/_layout.tsx:186).

6. **Reference docs lag source.** The design notes say commits have batches of at most 500; current mobile source chooses 50 per request and a server-side maximum is a different limit. Use source constants rather than importing prose as a performance specification. [Notes](/root/projects/hakgyo-v2/docs/mobile-sync.md:3), [actual client batch size](/root/projects/hakgyo-v2/apps/mobile/src/sync/engine.ts:47).

## Adaptation order for the Ethos plan

These are proposals, conditional on the separate Ethos/server comparison:

1. First establish correctness with sent-version acknowledgment, account-generation checks, single-flight work plus a guaranteed follow-up when writes arrive, and queue retention. Keep current storage/wire shapes wherever possible for the first OTA.
2. Add request metrics and structured error classification, then bounded backlog draining, jittered transient retry and reconnect/foreground scheduling. Measure request count, bytes, queue age, sync latency and conflict/retry rates; do not promise a percentage improvement without a baseline.
3. If current deltas or invalidation are expensive, introduce server-negotiated scoped revision/cursor capability with a legacy fallback. Preserve the previous endpoint and response fields through the rollout. Treat durable replay receipts and concurrent-entity conflict policy as server work when needed.
4. Use additive, idempotent transactional migrations for metadata. Retain existing outbox identity/payload until compatible clients can consume it; no table rename/drop, DB reset or destructive reserialization in an initial OTA. Test old DB → new JS → old JS rollback with pending operations intact.

Reference test ideas include offline retention, concurrent checkpoint coalescing, payload changes during upload, partial acknowledgments, no-progress server responses, splitting oversized legacy operations and retrying writes arriving during sync. [Engine test cases](/root/projects/hakgyo-v2/apps/mobile/src/sync/engine.test.ts:188), [legacy schema migration test](/root/projects/hakgyo-v2/apps/mobile/src/sync/store.test.ts:77). These inspected tests are useful starting points, not validation of an Ethos implementation.
